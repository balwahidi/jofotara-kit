# jofotara-kit

**[English](README.md)**

**بيئة التجربة التي لا يوفّرها نظام الفوترة الوطني — مع منشئ للفواتير، وعميل إرسال آمن، وأداة تحقق، ومهارة لوكلاء الذكاء الاصطناعي.**

لا يوفّر نظام الفوترة الوطني (JoFotara) التابع لدائرة ضريبة الدخل والمبيعات أي بيئة تجريبية. الطريقة الوحيدة لمعرفة إن كان ملف XML صحيحاً هي إرسال فاتورة حقيقية ببيانات اعتماد حقيقية، وهذا يُنشئ سجلاً ضريبياً حقيقياً. تتيح لك `jofotara-kit` أن تتأكد من كل شيء على جهازك أولاً:

- **`build` — منشئ الفواتير:** يحوّل بيانات البيع إلى فاتورة أو فاتورة إرجاع صحيحة: الأسعار الشاملة للضريبة، والخصم على السطر وعلى الطلب كاملاً، والبنود المعفاة والخاضعة لنسبة صفر، وشروط المشتري، والإرجاع الجزئي الذي يطابق مجموعه الفاتورة الأصلية تماماً.
- **`send` — عميل الإرسال:** يرسل الفواتير ويصنّف كل رد إلى: مقبولة، أو مرفوضة، أو غير معروفة، أو لم تُرسل؛ فلا تُعامَل مهلة الانتظار المنتهية على أنها رفض، ولا تُرسَل الفاتورة مرة ثانية فيتكرر السجل الضريبي.
- **`validate` — أداة التحقق:** تفحص ملف XML وفق قواعد الدليل الفني الرسمي للدائرة (الإصدار 1.4)، وتذكر لكل ملاحظة رقم الصفحة في الدليل وطريقة الإصلاح.
- **`serve` — خادم محاكاة محلي:** يحاكي `POST /core/invoices/` بالمسار والترويسات وشكل الطلب والرد نفسها، ويتذكّر ما قبله، فيرفض التكرار، والإرجاع لفاتورة غير موجودة، وإرجاع كمية أكبر مما بيع عبر عدة إرجاعات.
- **`template` — نماذج جاهزة:** فواتير ضريبة الدخل والمبيعات العامة وإرجاعاتها، نقدية وذمم، بالشكل الوارد في الدليل.

> هذه الأداة غير تابعة لدائرة ضريبة الدخل والمبيعات. نجاح الفاتورة في `jofotara-kit` يعني أنها "تطابق القواعد المعروفة"، لا أن الدائرة قبلتها.

## التثبيت

تحتاج إلى Node.js بالإصدار 22.18 أو أحدث.

</div>

```bash
npm install jofotara-kit
```

<div dir="rtl">

## البدء السريع

</div>

```bash
npx jofotara-kit template invoice > invoice.xml
npx jofotara-kit validate invoice.xml
npx jofotara-kit serve --port 8080
```

<div dir="rtl">

ثم اجعل عنوان الخادم في نظامك `http://127.0.0.1:8080` بدلاً من `https://backend.jofotara.gov.jo`، ولا يتغير شيء آخر.

## إنشاء الفواتير

صِف عملية البيع، ويتولّى المنشئ حسابات الفوترة الوطنية ويكتب ملف XML يجتاز كل القواعد.

</div>

```ts
import { buildInvoice, buildCreditNote } from 'jofotara-kit';

const invoice = buildInvoice({
  id: 'INV-1001', icv: 57,
  seller: { taxNumber: '…', name: '…', incomeSourceSequence: '…' },
  pricesIncludeTax: true,
  lines: [
    { name: 'قهوة', quantity: 3, unitPrice: 2.5, taxRate: 16, discount: { percent: 10 } },
    { name: 'خبز', quantity: 2, unitPrice: 0.75, taxRate: 0, taxCategory: 'Z' },
  ],
  orderDiscount: { amount: 1 },
});
// invoice.xml, invoice.body, invoice.document
```

<div dir="rtl">

- `id` رقم فاتورتك، و`icv` هو عداد الفواتير الذي تحتفظ به لكل مصدر دخل (1، 2، 3…).
- `seller`: الرقم الضريبي، والاسم كما هو مسجّل لدى الدائرة، و**تسلسل مصدر الدخل** من بوابة الفوترة.
- `pricesIncludeTax`: الأسعار شاملة للضريبة كما على الرف؛ يستخرج المنشئ الضريبة بدقة، فيساوي مجموعُ كل سطر مع ضريبته ما دفعه الزبون تماماً.
- `orderDiscount`: خصم على الطلب كاملاً؛ لا يقبل النظام إلا الخصم على مستوى السطر، فيوزّعه المنشئ على البنود بالتناسب.
- `invoice.body` هو جسم الطلب الجاهز للإرسال، و`invoice.document` يحتوي كل المبالغ المحسوبة.

### ما يتولاه المنشئ

- **الحساب:** حساب دقيق بأجزاء المليون من الدينار، والمبالغ تُكتب بست خانات عشرية.
- **فئات الضريبة:** `S` بنسبة من النسب المعتمدة (1، 2، 3، 4، 5، 7، 8، 10، 16)، أما البند بنسبة 0٪ فيجب أن يحدد `Z` (معفى) أو `O` (خاضع لنسبة صفر). تُرفض أي نسبة أخرى قبل كتابة أي XML.
- **المشتري:** الافتراضي زبون نقدي (`TN` برقم `0`)، ويُشترط اسم المشتري لفواتير الذمم وللفواتير النقدية التي تتجاوز 10,000 دينار.
- **الأخطاء:** يرمي المنشئ خطأ `BuildError` ورمزه `code` هو القاعدة التي كانت ستُخالَف، مثل `JOF-STA-005` عند إرجاع كمية أكبر مما بيع.

## الإرجاع (فاتورة الإرجاع)

يُبنى الإرجاع من ملف XML للفاتورة الأصلية الذي أرسلته واحتفظت به:

</div>

```ts
const ret = buildCreditNote({
  original: storedInvoiceXml,
  previousReturns: [storedReturnXml],
  lines: [{ lineId: 1, quantity: 1 }],   // أو 'all' لإرجاع كل ما تبقّى
  reason: 'إرجاع من الزبون', id: 'RET-1001', icv: 58,
});
```

<div dir="rtl">

- يعكس الإرجاع الفاتورة الأصلية: أرقام السطور الأصلية، والأسماء، والأسعار، وفئات الضريبة، والمشتري، ونوع الفاتورة (012 → 012، 022 → 022، 011 → 011، 021 → 021).
- تُضاف تلقائياً الحقول الإضافية التي يشترطها الدليل لإرجاع المبيعات العامة.
- مع `previousReturns` تُحسب الكميات التي أُرجعت سابقاً، ويُرفض إرجاع كمية أكبر مما بقي.
- آخر إرجاع لكل سطر يأخذ ما تبقّى بالضبط، فيطابق مجموع الإرجاعات الفاتورة الأصلية حتى آخر فلس.

احتفظ برقم UUID لكل فاتورة ترسلها. إن أردت إعادة المحاولة بعد انتهاء مهلة الانتظار فأرسل ملف XML نفسه. الدالة `readDocument(xml)` تقرأ أي فاتورة محفوظة وتعيد مبالغها.

**ضريبة المبيعات الخاصة (013/023)** مبنية وفق معادلات الدليل (الصفحات 56–80)، لكنها لم تُجرَّب بعدُ على النظام الحقيقي، ويذكر المنشئ ذلك في `warnings`.

## الاستخدام من أي لغة برمجة

يأخذ الأمر `jofotara-kit build` الحقول نفسها بصيغة JSON، فيمكن استدعاؤه من PHP أو .NET أو Python أو Java:

</div>

```bash
npx jofotara-kit build invoice.json > INV-1001.xml
npx jofotara-kit build invoice.json --body
npx jofotara-kit build invoice.json --json
```

<div dir="rtl">

`--body` يطبع جسم الطلب بدلاً من XML، و`--json` يطبع الناتج كاملاً `{xml, body, document, warnings}`. في الإرجاع تُذكر الفاتورة الأصلية والإرجاعات السابقة بمسار الملف، نسبةً إلى ملف JSON:

</div>

```json
{
  "type": "credit-note",
  "original": "INV-1001.xml",
  "previousReturns": ["RET-1000.xml"],
  "lines": [{ "lineId": 1, "quantity": 1 }],
  "reason": "إرجاع من الزبون",
  "id": "RET-1001",
  "icv": 58
}
```

<div dir="rtl">

عند وجود خطأ ينتهي الأمر برمز الخروج 1 ويطبع رمز القاعدة والسبب.

## إرسال الفواتير

الخطر الحقيقي عند التشغيل الفعلي ليس ملف XML، بل الرد. انتهاء مهلة الانتظار لا يعني أن الفاتورة رُفضت، وإرسال فاتورة جديدة لعملية البيع نفسها قد يُنشئ سجلاً ضريبياً مكرراً. يصنّف العميل كل عملية إرسال إلى واحدة من أربع نتائج:

</div>

```ts
import { createClient, JOFOTARA_PRODUCTION_URL } from 'jofotara-kit';

const jofotara = createClient({
  baseUrl: 'http://127.0.0.1:8080',
  clientId: process.env.JOFOTARA_CLIENT_ID!,
  secretKey: process.env.JOFOTARA_SECRET_KEY!,
});

const outcome = await jofotara.submit(invoice);
```

<div dir="rtl">

`baseUrl` إلزامي عمداً: إما خادم المحاكاة المحلي، أو `JOFOTARA_PRODUCTION_URL` بقرار واعٍ. أما `Client-Id` و`Secret-Key` فتحصل عليهما من شاشة ربط الأجهزة في بوابة الفوترة.

| `outcome.status` | متى | ماذا تفعل |
|---|---|---|
| `accepted` مقبولة | نجاح HTTP **و**حالة نجاح صريحة **و**رمز QR | احفظ `outcome.qr` والرد كاملاً، واطبع رمز QR على الفاتورة. |
| `rejected` مرفوضة | رفض صريح (`NOT_SUBMITTED` أو `ERROR` أو قائمة أخطاء) دون أي دليل قبول، حتى لو جاء مع HTTP 200 | اعرض `outcome.errors`، ثم أصلح وأعد الإرسال. |
| `unknown` غير معروفة | انتهاء المهلة، أو انقطاع الاتصال، أو رد غير مقروء، أو خطأ 5xx، أو نجاح دون رمز QR، أو رد متناقض | **لا ترسل فاتورة جديدة لعملية البيع هذه.** تحقّق من البوابة، وإن أعدت المحاولة فأرسل ملف XML نفسه (رقم UUID نفسه). |
| `not-sent` لم تُرسل | فشلت الفاتورة في التحقق، أو تعذّر الوصول إلى الخادم أصلاً | لم يُسجَّل شيء؛ أصلح وأرسل. |

يتحقق العميل من الفاتورة قبل إرسالها، ولا يعيد المحاولة من تلقاء نفسه، ولا يضع المفتاح السري في أي نتيجة. الدالة `classifyResponse(status, body)` تطبّق القواعد نفسها على رد حصلت عليه بطريقتك الخاصة.

من سطر الأوامر، تُرسل الفواتير بالترتيب ويتوقف الإرسال عند أول فاتورة لم تُقبل، فلا يُرسَل إرجاع بعد فشل فاتورته:

</div>

```bash
npx jofotara-kit serve &
npx jofotara-kit send INV-1001.xml RET-1001.xml
```

<div dir="rtl">

يذهب الإرسال إلى خادم المحاكاة افتراضياً. الخيار `send --production` يرسل إلى النظام الحقيقي، ويأخذ بيانات الاعتماد من متغيرات البيئة `JOFOTARA_CLIENT_ID` و`JOFOTARA_SECRET_KEY` فقط (وليس من سطر الأوامر، حتى لا تُحفظ في سجل الطرفية). رموز الخروج: 0 مقبولة، 1 مرفوضة أو لم تُرسل، 3 غير معروفة.

## للمطوّرين الذين يستخدمون وكلاء الذكاء الاصطناعي

يوفّر الأمر `jofotara-kit mcp` خادم MCP بالأدوات `build_invoice` و`build_credit_note` و`validate_invoice` و`get_template` و`list_rules` و`explain_rule`، وتعلّم المهارة المرفقة في `skills/jofotara` وكلاءً مثل Claude Code وCursor كيف يعمل النظام، وتجعلهم يتحققون من مخرجاتهم بدلاً من التخمين.

## قواعد لا تتهاون فيها

- لا يوجد نظام تجريبي حكومي: **لا ترسل فواتير تجريبية إلى النظام الحقيقي أبداً.** جرّب على خادم المحاكاة.
- لا تحفظ `Secret-Key` في الشيفرة ولا تطبعه في السجلات.
- احفظ لكل فاتورة: ملف XML المُرسَل، ورقم UUID، والرد كاملاً؛ فالإرجاع يحتاج إلى الفاتورة الأصلية.
- النتيجة "غير معروفة" ليست رفضاً: تحقّق قبل أي إعادة إرسال.

## المساهمة

أثمن مساهمة هي **رد حقيقي من نظام الفوترة**، خصوصاً رفضاً لم تتوقعه الأداة، مع ملف XML بعد حذف البيانات الحساسة (الأرقام الضريبية، والأسماء، وتسلسل مصدر الدخل). بهذا تتحول القواعد المستنتجة إلى قواعد مؤكَّدة. لا تشارك أبداً `Client-Id` أو `Secret-Key`.
